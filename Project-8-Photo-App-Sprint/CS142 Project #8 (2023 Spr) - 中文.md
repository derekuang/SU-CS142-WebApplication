# 提示

从设计上讲，用户故事并不是对某个功能的明确无歧义的规格说明。这意味着作为工程师的你需要在故事没有规定具体做法的部分，选择一个合理的方案来补齐细节。一条指导原则是回答这个问题：“应用的用户会希望这个功能做什么？”

# 评分

要获得本作业的满分，你需要完成总计**至少 12 个故事点（相当于 75 个作业分）**的故事。你超出 12 个故事点所做的任何故事点都将按作业分计算（即，超过 12 个故事点的部分换算率为 1 个故事点 \= 1 个作业分）。你可以额外提交总计最多 18 个故事点的故事。换句话说，通过总共完成 30 个故事点，你最多可以获得 18 分的额外加分。**我们只会在评分计算中计入 5 个故事**。

我们计划对部分实现的故事在部分分上非常吝啬。一个把较少故事完整做完的策略，会比一个把更多故事部分完成的策略表现更好。

请注意，如果你使用 npm 获取任何新包，请务必将其添加到 package.json 文件中（使用 \--save 选项即可为你完成这一点）。如果你不用 npm 获取某些东西，请把它放在你的 project8 目录中，以便为你的作业评分的课程工作人员能够使用它。

为了帮助我们对本作业评分，你需要就你所实现的故事提供说明。project8 的 zip 文件下载了一个 submission.txt 文件。submission.txt 中包含一份需要你填写的表单，用来收集我们需要的信息。这包括你的故事点计算、各故事所值的分数，以及你获得的总故事点。

**除了 submission.txt 文件之外，你必须提交一段关于你的照片应用及你所实现故事的简短视频导览。视频长度不应超过 12 × *k* 秒，其中 *k* 是你完成的故事点数。典型的视频长度在 2 分钟或更短。** 这应该是一段带音频的简单屏幕录制。在 macOS 上你可以使用 QuickTime，在 Windows 上你可以使用 VLC 进行屏幕录制。**请不要在制作视频上花费太多时间。我们不会对制作质量进行评分。**

长度接近最大允许值的视频很可能会因体积过大而无法通过我们的提交流程，因此我们需要你在 submission.txt 文件中提供一个链接。把视频上传到诸如 [YouTube](https://www.youtube.com/) 或 [Vimeo](https://vimeo.com/) 这样的视频分享网站，是获得此类链接的一种简单方式。作为评分流程的一部分，我们原本计划在课程讨论论坛上分享一些我们最喜欢的视频。请在 submission.txt 文件中注明你是否允许我们分享你的视频。

# 风格分（5 分） {#style-points-(5-points)}

如果你的问题解决方案具有恰当的 MVC 分解、遵循 MEAN 技术栈约定，并且是**无 ESLint 警告的 JavaScript，那么你将获得这些分数。你需要在提交前运行 \`npm run lint\`。** 此外，你的代码和模板必须整洁易读，你的网页在外观和便利性上必须至少“还算不错”。

注意：当安装并非来自 npm 的依赖时（例如来自 bower），请修改 package.json 文件，使脚本命令 \`npm run lint\` 也排除包含你依赖的文件夹。这样，ESLint 命令只会检查你自己的 JS 文件，并跳过与你所用库/依赖对应的任何 JS 文件（它们可能无法通过 linter）。

# 评论中的 @提及 {#@mentions-in-comments}

## 故事点：6

## 用户故事：

用户应能在照片的评论中 @提及用户，并能看到所有 @提及了某个特定用户的照片。

* 增强添加评论支持，使其允许 @提及任何已存在的用户。在评论文本框中应有一种智能的方式来选择用户（见提示）。
* 用户不应能 @提及一个无效（不存在）的用户，而对无效用户的 @提及也不应导致应用崩溃。
* 扩展用户详情视图，以显示所有含有 @提及该用户的评论的照片列表，或者在没有 @提及时显示一些合理的内容。@提及列表中的每一项都应包含：
  * 照片的小缩略图。点击照片应链接到该照片在用户照片页面上的*位置*。
  * 照片所有者的姓名。点击所有者姓名应链接到所有者的用户详情页。

## 提示：

* React Mentions：[https\://github.com/signavio/react-mentions](https://github.com/signavio/react-mentions)（React）

请注意，@提及被选中时与评论被提交时是有区别的。你可能需要想个办法在选中时于评论文本中标记出该 @提及。

你将需要修改数据库，以存储与特定照片相关联的 @提及。让 API 调用能够向照片添加 @提及，并返回所有 @提及了某个用户的照片，这可能会很有用。

# 照片的可见性控制 {#visibility-control-of-photos}

## 故事点：4

## 用户故事：

用户在上传照片时，应能限制哪些用户可以看到某张照片及其评论。该功能应按如下方式工作：

* 当用户上传照片时，应给他们一个*选项*，用于指定一份可以查看该照片的用户列表（共享列表）。如果未指定列表（即用户拒绝指定列表这一选项），那么该照片应可被所有人看到。
* 如果一张照片关联了共享列表，那么只有该照片的所有者以及列表上的人才能看到该照片。如果登录用户不在共享列表上，则该照片不应反映在显示给该登录用户的任何照片计数中。
* 如果共享列表为空，那么只有该照片的所有者才能看到该照片。请注意，这与“未指定列表”是不同的。

## 提示：

* 你将需要修改你的 schema，以存储某张照片的相关权限。
* 你将需要修改返回照片的查询，使其只返回用户有权查看的照片（即，不要在前端控制器中过滤照片）。

# 活动流 {#activity-feed}

## 故事点：4

## 用户故事：

用户应能看到照片分享网站上所发生活动的列表。该功能必须满足以下要求：

* 工具栏上一个标有“Activities”的按钮应把用户带到一个视图，该视图按时间倒序（最新的在最上面）显示网站上最近发生的 5 个活动。请注意，所显示的活动不必唯一（例如，可以有 5 个照片上传活动）。
* 每个活动条目应显示该活动的日期和时间、执行该活动的用户名、活动类型（即，照片上传、新评论等），以及如下一些活动特定信息：
  * 照片上传 \- 显示该照片的小缩略图
  * 添加评论 \- 显示评论所留在的那张照片的小缩略图
  * 用户注册 \- 无额外信息
  * 用户登录 \- 无额外信息
  * 用户登出 \- 无额外信息
* 活动显示视图应在有新活动发生时自行更新，或提供一个刷新按钮以便用户触发更新。

## 提示：

* 你将需要扩展数据库 schema，以存储已执行活动的记录。这可以通过多种方式实现，但为每条记录创建一个新对象的方式与 MongoDB 十分契合。计算活动历史可以通过对活动记录对象进行查询来完成。
* 你不需要为已存在的评论和照片（在已播种的数据库中）设置活动流条目。

# 删除评论、照片和用户 {#deleting-comments,-photos,-and-users}

## 故事点：4

## 用户故事：

用户应能删除他或她在网站上拥有的任何东西。这包括：

* 他/她的任何照片
* 他/她所做的任何评论（这包括在其他用户照片上所做的评论）
* 整个用户账户。如果用户选择删除他/她的账户，应有一个最终的警告提示，随后用户被登出，并且他/她账户的所有细节都从数据库中销毁。这意味着，除了 User 对象被销毁之外，你还应处理删除该用户创建的所有照片和评论。本质上，我们会将该视作用户从未存在过。为已实现的其他故事所添加的其他东西（例如，活动、可见性、提及等）也应一并处理。

## 提示：

* 当用户删除各种对象时，你需要考虑也必须一并删除的任何关联信息。这将在服务器上完成，你可能需要研究一下如何正确地销毁带有关联关系的对象。
* 确保用户不能删除任何他或她并不拥有的东西。

# 照片“点赞”投票 {#photo-“like”-votes}

## 故事点：4

## 用户故事：

* 类似于 Facebook 的点赞按钮，为每张照片实现一个点赞按钮，以允许用户点赞该照片（可以是按钮、[图标](https://material.angularjs.org/latest/api/directive/mdIcon)等）。
* 点击点赞按钮会让用户点赞该照片（并在视觉上把点赞按钮变为取消点赞按钮）。对一张已被同一用户点赞过的照片点击取消点赞按钮，应取消该照片的点赞。
* 一张照片的点赞数永远不应大于用户总数。
* 如果某用户已经点赞过一张照片，页面上应有某种视觉提示表明该用户已经点赞过该照片。如果用户取消点赞该照片，则应移除该视觉提示。
* 在点赞按钮旁边，应显示该照片的点赞数。这一计数应在点赞或取消点赞照片时立即（在视觉上）更新。
* 用户的照片页面应按点赞数降序排列（点赞最多的照片在最上面）。如果照片点赞数相同，则按时间戳倒序排列（最新的在前）。这不需要在用户点赞或取消点赞照片时立即改变——你可以等到页面刷新。

## 提示：

* 你将需要更新 schema，以包含与某张照片关联的点赞以及创建这些点赞的用户。
* 你将需要在服务器上执行校验，以确保每个点赞都是有效的。此外还要研究一下[竞态条件](https://en.wikipedia.org/wiki/Race_condition)，并判断在大规模系统中这是否会带来任何潜在问题。

# 用户的照片收藏列表 {#favorite-list-of-photos-for-users}

## 故事点：6

## 用户故事：

已登录的用户应能收藏照片，并在一个新页面（路径：/favorites）上显示一份特定于该用户的收藏列表。该页面应专门用于显示该用户已收藏照片的列表。用户应能从该列表中移除已收藏的照片。
用户应能通过在任意用户的照片列表中所显示的任意照片旁边点击一个按钮，直观地将任何照片标记为收藏。某张照片被收藏期间：

* 该用户照片列表上用于收藏该照片的按钮应被禁用。
* 应有某个明确的提示表明该照片当前已被该用户收藏。

在一个新的视图组件上，用户应能看到一份已收藏照片的列表，该列表必须满足以下规格：

* 每张照片都必须由一个小缩略图来表示。
* 点击缩略图应弹出一个[模态窗口](https://www.google.com/search?q=modal+window&source=lnms&tbm=isch&sa=X&ved=0ahUKEwjryM6TmPTMAhVD-2MKHamgARIQ_AUIBygB&biw=1920&bih=962)，显示该图片的更大版本（见下方提示）。仅仅让点击把用户导向一个只包含该照片的新页面是**不够**的。
* 模态窗口还应包含一段标题（caption），内容为该图片所关联的日期。
* 应有一种直观的方式将某张照片从列表中移除（例如，点击缩略图右上角的“x”），使其不再属于该用户的收藏列表，即使用户刷新页面并重新登录后也是如此。

其他说明：

* 已收藏照片的列表应能通过 url 路径 /favorites（\#\!/favorites 或 \#/favorites）访问。
* 根据用户是否已登录，有条件地在侧边导航或顶部工具栏中显示指向收藏页面的导航 UI。
* 这份已收藏照片的列表必须在多次会话之间保持：即，你必须使用服务器端数据库来跟踪这份列表，并在用户访问其收藏页面时访问该信息来构建列表。

# 给照片打标签 {#tagging-photos}

## 故事点：10

## 用户故事：

用户应能在照片中给人物打标签。以下是这个新功能应当如何表现的粗略草图：

* 用户可以通过选中照片中的一个矩形区域，并识别所选区域中的人物，来给照片*打标签*。
* 该矩形通过在照片上拖动鼠标来选中。当用户拖出该区域时，矩形必须能够拉伸和收缩。用户必须能够朝任意方向拖动，且矩形在拖动完成后必须保持可见。
* 如果用户试图把矩形扩展到图片范围之外，你必须把矩形裁剪到图片边界内。
* 如果用户不喜欢所选中的矩形，他们可以选择另一个来替换它。
* 一旦用户选中了照片的一个区域，他们应能从系统已注册用户中选择一个姓名并给该用户打标签。该标签可以提交并记录到数据库中。
* 一张照片可以有多个标签，每个标签都有自己的矩形和用户名。
* 应用必须提供一种显示带有其所有标签的照片的机制：每个标签的矩形应显示在照片之上，当鼠标悬停在该矩形上时，应显示被标记用户的名字和姓氏。
* 点击用户名应把视图切换到被标记用户的用户详情视图。

## 提示：

* **这值 10 个故事点，因为它很难！** 在前端，它要么需要找到某个区域选择模块并让它工作，要么需要构建你自己的区域选择机制。我们建议你选择别的故事，除非你对这个挑战感到兴奋。
* 每张照片的标签都应关联到照片中的相对位置。这将使你能够使用相对定位来正确显示标签。
* 在页面滚动到不同位置时测试给照片打标签，以确保位置计算对窗口滚动位置不敏感。
* 某些第三方库可能期望你提供图片的宽度和/或高度。
